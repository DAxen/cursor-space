3.2 项目知识库落地思路：落地方案

结论：三个工作包按依赖递进——存量资产组织化（纯文档工作，立即见效）→ C/C++ 结构层（工程量小、价值高）→ 闭环与保鲜机制（决定知识库存亡）；"一次写对"的天花板由第三个工作包决定。
工作包① 存量资产组织化
纯文档工作 · 零基础设施依赖
  • 盘点 docs / specs / skills 存量，建 docs/wiki/ 目录树
  • 编写 index.md 总目录：每页一行链接 + 一句话摘要，按类别组织（Karpathy 模式核心件）
  • CLAUDE.md 瘦身分层：根文件只留跨域硬约束 + 命令 + 检索协议；模块目录放局部 CLAUDE.md
  • 用 deep-wiki 类 skill 自动生成初稿，架构页 / 约束页人工评审后才收编
产出：可导航的分层 wiki + 瘦身后的宪法层
工作包② C/C++ 结构层
工程量小 · 大仓价值最高
  • 生成 compile_commands.json（CMake 一个开关；其他构建系统用 bear / compiledb）
  • 部署 clangd MCP Server（clangd-mcp-server，Chromium 级大仓开箱即用；超大仓可选 remote-index）
  • CLAUDE.md 加路由规则："符号查找用 LSP 工具；字符串 / 注释 / 日志检索才用 grep"（最易遗漏的一条）
  • 验证：让 Agent 做一次跨模块引用追踪，对比 grep 与 LSP 的上下文消耗
产出：编译器级符号导航，替代"自建知识图谱"
工作包③ 闭环与保鲜机制
决定知识库存亡 · 复利来源
  • OpenSpec 联动：/opsx:archive 归档变更时同步检查受影响 wiki 页；spec delta 合入时更新架构页
  • 错误回写：Agent 犯错 → 修正 → 教训写进 pitfalls/ 或约束页（一句话即可）
  • CI 巡检：wiki lint（死链、目录一致性），搭 openspec validate 的车
  • 痛点观测：记录检索失败案例；"概念找不到"高频出现时，再评估向量层
产出：知识随代码演进而复利，不腐化
两个关键闭环（比任何检索基础设施都更接近"一次写对"）
